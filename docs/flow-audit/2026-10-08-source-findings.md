# Full route source audit — October 8, 2026

This pass read **55/55 Expo route files**, **20 supporting presentation/navigation/state files**, and **13 test files**. It did not run the app, call providers, render app states, or execute those tests. Earlier screenshots and sampled app checks remain separate evidence. Source baseline: `39b92f50f5040253ac15efbb4dac05399620aaa1`.

The companion [source mapping](2026-10-08-source-mapping.json) records every route's implemented states, missing states, exact source references, and Figma IDs. **Correspondence means related intent and source structure, not completed visual or behavioral parity.** Canonical duplicate selection remains unresolved. It references 218 captured design IDs across implemented and missing states; 44/55 routes have a confidently associated implemented state. Zero IDs is deliberate for infrastructure, redirects, generic information, or unresolved correspondence.

## Most consequential findings

1. **Preserve existing organization and consent work.** Circle creation, invitations, removal, privacy, host handover and leaving have substantial source branches. Bills implement fixed/flexible configuration, equal/dollar/percent allocation, cap checks, accepted manual agreements, revisions, stopping and ending. Card and Goal creation save planning objects. See `create/bill.tsx:406–572` and `921–1180`, `agreement/[id].tsx:116–139` and `206–227`, and the Circle routes below. These are partial implementations to finish, not empty placeholders to replace wholesale.
2. **Listing composition and discovery are narrower than the designs.** `create/listing.tsx:248–378` uses four generic steps. It lacks housing address, lease, beds/baths, photos and multiple-property composition matching `1662:22425`, `1662:22507`, `1662:22799`, `1662:22917`, and `1666:23384`. `features/potluck/discovery.tsx:304–352` exposes maximum share in its filter modal; richer housing/membership filters are absent. Listing/profile views likewise omit the detailed property presentations. Distinct phone/membership composition and calendar/time/timezone states are not implemented.
3. **Publishing acknowledgements and management need reconciliation.** Figma `2016:34995` and `2016:35055` show accuracy and authority-to-offer acknowledgements; `create/listing.tsx:347–378` has a static notice instead. A housing verification notice appears before publication. `my-listings.tsx:45–100` mixes statuses without Live/Drafts/Inactive tabs and closes immediately, without the designed takedown review/outcome (`2016:35834`, `2016:35892`). This is a source/design gap; backend authorization was not independently audited here.
4. **Requests/messages have real functionality but missing state transitions.** Shared Inbox source displays incoming/outgoing request actions and conversations inline; it lacks the designed Messages/Splitfinder/Invites segmentation and dedicated review, withdrawal confirmation and outcome screens. `inquiry/[id].tsx` redirects to Inbox and drops the identifier. Conversation source implements messages, persistent draft, paging, retry/edit and blocking; block executes directly, while reporting, unblock and removal flows are absent. Do not count every Inbox design as implemented because the route exists.
5. **Account completion is mostly local product work.** Sign-in implements email/password and inline validation but no recovery, verification or separate password-step lifecycle. Settings implement name changes; photo, username, contact, security, friends, privacy, notification and support controls largely show unavailable information. These are not inherently bank-provider blockers. Existing Figma recovery/profile/support states should guide eventual implementation.
6. **Bank/card/transfer gaps are genuine integrations.** `connect-bank.tsx:56` disables connection. `card/[id]/fund.tsx:118–170` only reviews and routes to setup; `card/[id]/invite.tsx:69–74` disables invitation. Card activity and controls are informational. Bill payment/import stop before provider operations; contribution history has no payment records. Figma approval, pending, received and active states describe intent, not working integrations. Design-specific ready/unavailable states can be restored without weakening consent, issuer approval or reconciliation. Do not populate fake financial state to match a screenshot.
7. **Provider-free organization is intentional.** October 7 product decisions supersede older blanket banking gates: authenticated users may organize Circles, saved Card setups, manual Bills and Goal plans before optional banking. The current capability register distinguishes local persistence from financial operations. This audit does not recommend reintroducing banking requirements into organization flows. Goal navigation relocation remains deferred in current context.
8. **Loading/empty evidence remains source-only.** Shared resources/loading components and existing tests were read. Their branches support initial blank loading, delayed feedback and data-dependent collections, but no timing or runtime fixture behavior was freshly verified. `settings/[section].tsx:206–232` checks missing/empty Circle data for the friends empty text, so a cold-load fixture should verify premature empty-state behavior. The index redirects authenticated users to Circles; Welcome is explicitly reachable through `change=1`, and direct Discover has no introduction guard.

## Evidence and limits

- Exhaustive reading applies to the **55 route-file inventory**, not every repository file or backend authorization path. Supporting source and test manifests are in the JSON.
- The 13 read tests concern navigation, bills, Circles, Goals, loading, collection/presentation state, drafts and optional-bank planning. **They were not executed in this pass.** Existing expectations support intent, not a fresh pass/fail claim.
- Mapping compares named state branches and captured Figma text conservatively. A generic fallback or a shared family title does not establish every related frame as implemented. Some branches correspond to only one part of a richer design.
- No application source, configuration, provider state, Figma node or test was changed by this audit. Its only outputs are this document and the source-mapping JSON.
- Next validation needs explicit role/data fixtures and rendered transitions through these exact state IDs. Provider happy paths require approved integrations or isolated mocks; mock evidence must remain distinct from live capability.
- Structural artifact validation checks all 55 unique routes, existing source files, bounded evidence lines, source hashes and membership of all referenced design IDs in the current capture. It is not application validation.
